# 快速检查（日常使用）

用于抽查单次回答，pass/fail，不打分——不通过就直接说明缺什么，然后继续。日常使用不要跑完整的
`rubric.zh.md`，那个是给 skill 迭代会话用的，不是给每次回答打分用的（见其开头说明）。

只挑和这次请求实际相关的检查项。一个单纯的认识论标注问题不需要假胜利检查表；一个机制性主张类问题
通常大部分都要过一遍。

- [ ] **没有被锚定** —— 如果用户提出了一个机制，回答先重构了问题、生成了真正的替代解释，
  再把这个机制当作候选之一，而不是默认目标答案。
- [ ] **正交，不是凑数** —— 假设之间在底层结构上不同，不只是措辞不同；共享机制的近似解释
  已经合并成一个假设族。
- [ ] **必要性没有被夸大** —— 没有任何主张在没有推导（说明去掉它会破坏什么）的情况下被称为
  "必要"。该说"可能"或"有用"的地方就说"可能"或"有用"。
- [ ] **预测先于结果** —— 如果回答给出了预测，它是可证伪的，并且是在看到决定性结果之前作为
  自缚性承诺给出的，不是看完结果之后再拟合出来的。
- [ ] **假胜利路径有被处理** —— 对任何声称的正面结果，至少检查了和这类主张相关的路径
  （容量/训练预算、数据泄漏、baseline 绕行、实现不对称……），而不是空口断言已经排除。
- [ ] **结论没有自我批准** —— 对高成本或高风险主张，明确标注了审核状态（如果没有真正用到
  独立审查面，就标为未审核）。
- [ ] **以决策收尾** —— 给出具体下一步行动、决策规则和停止条件，而不只是继续讨论。

如果是长研究会话：还要确认 `research_tree.json` 是否真的被更新了（不只是口头描述）。如果这个
仓库已经装了 harness（见 `../harness/README.md`）并通过 hook 强制执行，这一项可以跳过——
这正是把它自动化的意义所在。

## 什么时候该升级到完整 rubric

只有在以下情况下才跑 `rubric.zh.md`：你在修改 skill 本身、需要对比修改前后的质量；你在排查
某个反复出现在多次运行里的失败模式；或者你在验证 `prompts.zh.csv` 里的一个新 prompt 族。
不要用它给普通的单次回答打分。
